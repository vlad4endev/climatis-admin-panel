
Цель: исправить поведение в «Материалы» у расчёта так, чтобы выбранное наименование материала и суммы стабильно сохранялись при любом количестве строк и при переходах между вкладками (например, «Для заказчика» → обратно).

## Что происходит сейчас (причина бага)
В `src/components/estimates/MaterialListEditor.tsx` при выборе материала используется функция `selectMaterial()`, которая вызывает `updateMaterial()` несколько раз подряд:

- `updateMaterial(materialId, "materialId", ...)`
- `updateMaterial(materialId, "materialName", ...)`
- `updateMaterial(materialId, "pricePerUnit", ...)`

А `updateMaterial()` внутри использует массив `materials` из замыкания (тот, который был на момент рендера), и каждый вызов делает `onChange(materials.map(...))`.

Проблема: когда вызовов несколько подряд, они могут перетирать друг друга, потому что каждый следующий вызов строит обновление на “устаревшей” версии массива `materials`. В результате:
- на второй/третьей строке “слетает” `materialName`,
- где-то остаются количество/цена, но имя пустое,
- расчёт итогов начинает вести себя нестабильно (потому что часть строк/полей фактически откатывается).

Это классическая ошибка “stale state” (обновления состояния на основе устаревших данных), особенно заметная при нескольких строках и при быстрых действиях.

## Как исправим (идея)
Сделаем все изменения материалов “атомарными” и всегда основанными на актуальном состоянии:

1) Изменим тип пропса `onChange` в `MaterialListEditor` на setter-стиля React:
   - было: `onChange: (materials: Material[]) => void`
   - станет: `onChange: React.Dispatch<React.SetStateAction<Material[]>>`
   
   Почему это важно: тогда можно делать `onChange(prev => ...)`, и React гарантирует, что `prev` — актуальное состояние, а не устаревшая копия из замыкания.

2) Перепишем все операции изменения материалов на функциональные обновления:
   - `addMaterial`: `onChange(prev => [...prev, newMaterial])`
   - `removeMaterial`: `onChange(prev => prev.filter(...))`
   - `updateMaterial`: `onChange(prev => prev.map(...))`

3) В `selectMaterial` перестанем вызывать `updateMaterial` 2–3 раза подряд.
   Сделаем один вызов `onChange(prev => prev.map(...))`, который сразу установит:
   - `materialId`
   - `materialName`
   - `pricePerUnit` (аккуратно: обновлять и при цене `0`, поэтому проверка должна быть `selectedMaterial.price != null`, а не `if (selectedMaterial.price)`)

4) Аналогично в `handleSearchChange` сделаем одно обновление строки:
   - `materialName = value`
   - `materialId = undefined`
   чтобы ввод текста не конфликтовал с “выбранным” ID.

5) `searchValues` тоже переведём на функциональные апдейты там, где возможны быстрые последовательные изменения:
   - было: `setSearchValues({ ...searchValues, ... })` (тоже может быть stale)
   - станет: `setSearchValues(prev => ({ ...prev, ... }))`

## Где именно правим
Только фронтенд-логика выбора и изменения материалов:

- `src/components/estimates/MaterialListEditor.tsx`
  - поменять тип `onChange`
  - переписать `addMaterial/removeMaterial/updateMaterial/selectMaterial/handleSearchChange`
  - поправить проверку цены на `selectedMaterial.price != null`

- `src/components/estimates/EstimateForm.tsx`
  - изменений по логике, скорее всего, не потребуется, потому что туда уже передаётся `setMaterials`, который как раз подходит под `Dispatch<SetStateAction<Material[]>>`
  - возможно, понадобится лишь подправить типы TypeScript, чтобы не ругался на пропсы

## Проверки после фикса (чек-лист)
1) Создать расчёт → вкладка «Материалы»
2) Добавить 3 позиции:
   - в каждой выбрать материал из списка (клик по выпадающему)
   - заполнить количество/цену
3) Перейти на вкладку «Для заказчика» → вернуться на «Материалы»
   Ожидаем:
   - во всех строках сохранено имя материала
   - количество/цена на месте
   - сумма по строкам считается
   - итог “Итого” считается корректно и не обнуляется
4) Изменить имя вручную (не из списка) — убедиться, что:
   - `materialId` сбрасывается (это уже задумано логикой)
   - имя не пропадает после переключения вкладок
5) Быстро нажать “+” добавить несколько строк подряд — не должно быть “перетирания” строк и значений

## Почему это не сломает остальное
- Мы не меняем структуру данных `Material` и не меняем формат сохранения в базе.
- Мы делаем обновления состояния более корректными: вместо “пересобрать из устаревшего массива” используем “обновить от актуального prev”.
- Это локальная правка компонента редактора материалов и типизации его пропса; остальные подсистемы (включая сохранение, печать, «Для заказчика») продолжат получать те же данные, но теперь они будут стабильно заполнены.

## Дополнительно (если обнаружится второй источник)
Если после этого останутся редкие случаи “пропадания”, вторым шагом проверим, не происходит ли где-то ещё перезапись `materials` в `EstimateForm` при переключении вкладок (например, через авто-сохранение). Но по текущему коду первопричина именно в многократных `updateMaterial()` на базе stale `materials`.
